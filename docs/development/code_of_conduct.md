# Code of Conduct

> **Author:** Ali Emre Arlı
> **Module:** Documentation
> **Version:** 1.0.0
> **Last Updated:** 2026-10-19
> **Status:** Active

This project adopts this Code of Conduct to establish a respectful, professional, and technically focused environment for contributors, developers, maintainers, and community members.

The project values technical rigor, architectural consistency, portability, maintainability, and clear engineering standards. These values require an environment in which participants can exchange ideas, challenge technical decisions, identify defects, and disagree directly without being subjected to harassment or personal abuse.

This document defines the behavioral expectations applicable to participation in the project, identifies unacceptable conduct, and establishes the principles governing enforcement.

The Code of Conduct governs interactions between people. It does not restrict legitimate technical criticism, impose a requirement to agree with maintainers, or replace the technical requirements established by the coding style guide.

---

# 1. Purpose

The purpose of this Code of Conduct is to:

- Establish clear behavioral standards for project participation.
- Encourage professional, direct, and technically substantive communication.
- Prohibit harassment, discrimination, intimidation, and other abusive conduct.
- Protect the ability of contributors to participate without personal hostility.
- Define the responsibilities of maintainers when handling violations.
- Establish proportionate and consistent enforcement procedures.

The project recognizes that technical disagreement is a necessary part of software engineering. Participants MUST be able to challenge implementations, architectural decisions, specifications, and technical conclusions without being required to soften legitimate criticism merely to avoid disagreement.

At the same time, technical disagreement MUST NOT be used as justification for personal attacks, harassment, threats, or other prohibited conduct.

# 3. Definitions

The following terms have the meanings specified below when used in this document.

- **Participant:** Any person interacting with the project, including contributors, developers, maintainers, reviewers, and users.
- **Contributor:** A participant who submits code, documentation, tests, bug reports, proposals, or other project-related contributions.
- **Maintainer:** A person or authorized team responsible for maintaining project repositories, reviewing contributions, managing project resources, or enforcing project policies.
- **Project Space:** A repository, issue tracker, pull request, code review, mailing list, forum, chat channel, documentation platform, or other venue officially used for project activities.
- **Technical Criticism:** Evaluation of code, designs, specifications, implementations, technical claims, or engineering decisions based on relevant technical considerations.
- **Harassment:** Unwelcome conduct directed at an individual or group that constitutes intimidation, targeted hostility, discriminatory abuse, or other prohibited personal behavior.
- **Enforcement Action:** A measure taken by an authorized maintainer in response to a violation of this Code of Conduct.

# 4. Scope

This Code of Conduct applies to interactions conducted as part of the project, including:

- Official source code repositories, issue trackers, pull requests, and code reviews.
- Project-related mailing lists, forums, and communication channels.
- Project documentation, contribution guides, commit messages, and code comments.
- Official project meetings, presentations, and events.
- Public interactions in which a participant is acting in an official project capacity.
- Other venues explicitly designated as official project spaces.

This Code of Conduct primarily governs project-related interactions. It does not establish general authority over participants' private lives or unrelated personal communications.

Conduct occurring outside official project spaces MAY be considered when there is a clear and relevant connection to project participation, such as credible threats against project members, targeted harassment of contributors, or attempts to intimidate participants into withdrawing from project activities.

Any such consideration MUST be relevant to protecting the project community and MUST respect applicable law, privacy, and procedural fairness.

# 5. Our Standards

Participants MUST follow these standards when interacting within the project community.

## 5.1. Respectful Professional Conduct

Participants MUST treat other community members with professional courtesy and respect.

Disagreements MUST focus on relevant matters rather than personal characteristics, identity, status, or perceived worth.

Participants MUST NOT be subjected to abuse merely because they are inexperienced, hold a minority technical opinion, challenge a maintainer, or disagree with an established implementation.

• • •

## 5.2. Technical Integrity

Participants SHOULD support technical claims with relevant reasoning, evidence, specifications, reproducible results, or other appropriate sources.

Technical conclusions MAY be direct and unequivocal when supported by sufficient evidence.

Participants SHOULD acknowledge relevant uncertainty, limitations, and contradictory evidence rather than deliberately misrepresenting technical facts.

• • •

## 5.3. Professional Communication

Communication SHOULD be clear, relevant, and focused on the matter under discussion.

Participants SHOULD provide actionable feedback when requesting changes to a contribution.

Maintainers SHOULD explain the technical or procedural grounds for rejecting a contribution when such an explanation would reasonably help the contributor understand the decision.

• • •

## 5.4. Fair Participation

Participants MUST NOT use harassment, intimidation, or personal hostility to discourage legitimate participation.

Maintainers SHOULD evaluate contributions according to the project's published technical requirements, scope, and policies rather than personal relationships or irrelevant characteristics.

Contributors MUST NOT be guaranteed acceptance merely because they have invested substantial effort or disagree with a rejection. Maintainers retain the authority to reject contributions that do not meet project requirements.

• • •

## 5.5. Responsible Use of Project Resources

Participants MUST respect repository permissions, communication-channel rules, review procedures, and other legitimate project controls.

Participants MUST NOT deliberately disrupt project operations, misuse access privileges, or interfere with other contributors' ability to participate.

# 6. Unacceptable Behavior

The following conduct is prohibited within the scope of this Code of Conduct.

## 6.1. Personal Attacks and Abuse

Participants MUST NOT direct insults, degrading remarks, personal humiliation, or abusive language at other participants.

Criticism of a person's specific technical claim, implementation, or demonstrated misunderstanding is permitted under Section 7. Attacks on a person's dignity or worth are not.

• • •

## 6.2. Harassment and Intimidation

Participants MUST NOT engage in targeted harassment, threats, coercion, stalking, or sustained hostile behavior.

Unwelcome sexual attention, sexual harassment, and discriminatory abuse MUST NOT be tolerated.

Repeatedly targeting a participant after a clear request to stop MAY constitute a violation, depending on the nature and context of the conduct.

• • •

## 6.3. Discrimination

Participants MUST NOT harass, threaten, or abuse others on the basis of personal characteristics or background.

Technical participation MUST NOT be obstructed through discriminatory treatment unrelated to legitimate project requirements.

• • •

## 6.4. Privacy Violations

Participants MUST NOT publish or disclose another person's private or sensitive information without authorization or another legitimate basis.

This prohibition includes doxxing, disclosure of private contact details, exposure of credentials, and malicious disclosure of confidential information.

• • •

## 6.5. Disruptive Conduct

Participants MUST NOT deliberately obstruct project work through persistent spamming, repeated bad-faith derailment, coordinated harassment, or intentional interference with technical discussions.

Good-faith disagreement, repeated requests for clarification, and persistent technical objections are not inherently disruptive merely because they are inconvenient or unpopular.

• • •

## 6.6. Abuse of Authority

Maintainers and other participants with elevated permissions MUST NOT use their authority to threaten, harass, retaliate against, or unfairly target contributors.

Project permissions MUST be exercised for legitimate project purposes and in accordance with applicable policies.

• • •

## 6.7. Retaliation

Participants MUST NOT threaten, harass, or otherwise retaliate against individuals for making good-faith reports, participating in an investigation, or raising legitimate concerns about project conduct.

A report that is not substantiated does not, by itself, establish that the reporter acted in bad faith.

• • •

## 6.8. Deliberate Misrepresentation

Participants MUST NOT knowingly fabricate evidence, impersonate other participants, or deliberately misrepresent relevant facts to harass contributors, manipulate enforcement decisions, or disrupt project governance.

Good-faith mistakes, disputed interpretations, and technical conclusions that later prove incorrect are not automatically violations.

# 7. Technical Communication and Critical Disagreement

The project distinguishes between rigorous technical criticism and abusive personal conduct.

## 7.1. Legitimate Technical Criticism

Direct, rigorous, and strongly worded technical criticism is permitted.

Participants MAY challenge:

- The correctness of an implementation.
- Architectural decisions and module boundaries.
- Memory safety, undefined behavior, and resource ownership.
- ISO C compliance and portability assumptions.
- API contracts and ABI compatibility.
- Error handling, security properties, and failure behavior.
- Performance claims, benchmark results, and optimization strategies.
- The technical validity of another participant's reasoning or conclusions.

For example, the following statement is acceptable when relevant and technically justified:

> This implementation violates the ABI contract because the public structure layout is not stable across the supported compilers. The interface must be redesigned before this change can be accepted.

Likewise, participants MAY directly identify an incorrect technical understanding:

> This conclusion misunderstands the C11 rules governing object lifetime. The proposed pointer access is invalid after the object's lifetime ends.

Such statements MUST NOT be treated as personal attacks solely because they are direct, negative, or strongly worded.

• • •

## 7.2. Prohibition of Personal Abuse

Technical criticism MUST remain relevant to the technical matter under discussion.

Participants MUST NOT use a technical disagreement as an excuse for insults, threats, humiliation, discriminatory remarks, or harassment.

For example:

> You are an incompetent idiot, and nobody should listen to you.

This is a personal attack and is prohibited.

The distinction depends on the content, context, and purpose of the communication rather than whether the criticism is comfortable to receive.

• • •

## 7.3. Criticism of Technical Competence

A participant's technical understanding MAY be criticized when the criticism is relevant to a specific technical claim, implementation, or decision.

Such criticism SHOULD identify the misunderstanding, incorrect assumption, or missing requirement whenever reasonably possible.

A participant MUST NOT be protected from legitimate technical criticism merely because it identifies a significant error or a lack of understanding relevant to the work.

Conversely, assertions about competence MUST NOT be used as a pretext for personal humiliation or repeated targeted hostility.

• • •

## 7.4. Code Review Standards

Code review feedback SHOULD be direct, concise, technically justified, and actionable.

Reviewers MAY reject a contribution when it violates the coding style guide, fails to satisfy requirements, introduces unacceptable risks, or does not meet the project's standards.

Contributors MAY challenge review conclusions and request technical justification.

Reviewers MUST NOT use code review as a means of personal retaliation, intimidation, or harassment.

Maintainers SHOULD distinguish between mandatory corrections, recommendations, and matters of technical preference.

• • •

## 7.5. Disagreement with Maintainers

Participants MAY disagree with maintainers and challenge their technical or procedural decisions through appropriate project channels.

Disagreement with a maintainer MUST NOT, by itself, constitute a Code of Conduct violation.

Maintainers MAY make final decisions within their assigned authority and applicable project governance rules. Those decisions MUST NOT authorize harassment, discrimination, or retaliation.

# 8. Enforcement Responsibilities

Maintainers responsible for enforcing this Code of Conduct MUST exercise their authority fairly, consistently, and proportionately.

## 8.1. Clarification of Standards

Maintainers MUST make this Code of Conduct reasonably accessible to participants and SHOULD clarify its application when genuine uncertainty arises.

• • •

## 8.2. Review of Reports

Reports of potential violations MUST be considered in a timely and impartial manner.

Maintainers SHOULD assess the available information, relevant context, severity, frequency, and potential impact of the reported conduct.

Where practicable, enforcement decisions SHOULD avoid relying exclusively on isolated excerpts when surrounding context is necessary to understand the incident.

• • •

## 8.3. Confidentiality

Reports and investigations MUST be handled with appropriate confidentiality.

Information SHOULD be disclosed only to individuals who need it to assess the report, protect participants, or implement an enforcement decision, subject to applicable legal and safety requirements.

Absolute confidentiality MUST NOT be promised where disclosure may be necessary to address a serious safety concern or comply with applicable law.

• • •

## 8.4. Moderation Authority

Within their authorized responsibilities, maintainers MAY:

- Request that a participant correct or remove inappropriate content.
- Reject contributions that violate project requirements or policies.
- Remove or hide inappropriate comments where platform permissions allow.
- Close discussions that have become abusive or irrecoverably disruptive.
- Temporarily restrict participation in project-controlled spaces.
- Revoke project access or impose a permanent ban when justified.

Such actions MUST be consistent with the project's governance and access-control policies.

Maintainers MUST NOT arbitrarily alter contributors' source code or commit history without the authorization required by the relevant repository procedures.

• • •

## 8.5. Impartiality and Conflicts of Interest

A maintainer who is directly involved in a reported incident SHOULD NOT act as the sole decision-maker for that incident when another suitable, impartial maintainer is available.

Where possible, enforcement decisions SHOULD be reviewed by an uninvolved maintainer or another authorized project representative.

• • •

## 8.6. Accountability

Enforcement decisions SHOULD have an identifiable rationale and a record appropriate to the severity of the incident.

Maintainers SHOULD apply comparable measures to materially similar incidents while accounting for relevant differences in severity, context, and prior conduct.

# 9. Enforcement Guidelines

Violations MAY result in corrective or disciplinary measures. The appropriate response MUST be determined according to the severity, context, frequency, impact, and relevant history of the conduct.

The measures below provide a general framework. They do not require maintainers to apply every stage sequentially when the seriousness of an incident warrants a more immediate response.

## 9.1. Correction

**Typical circumstances:**

- Minor or isolated inappropriate conduct.
- An unintentional breach of communication expectations.
- A discussion that has become unnecessarily hostile but can reasonably be corrected.

**Possible measures:**

- A request to correct or remove the problematic content.
- A private explanation of the applicable rule.
- A request to acknowledge the issue or apologize where appropriate.

Correction is intended to resolve minor violations and prevent recurrence rather than impose unnecessary punishment.

• • •

## 9.2. Warning

**Typical circumstances:**

- A clear violation of this Code of Conduct.
- Repeated minor violations.
- Continued inappropriate behavior after a corrective request.

**Possible measures:**

- A formal written warning.
- An explanation of the violation and the expected corrective behavior.
- Notice of the possible consequences of further violations.

Warnings SHOULD identify the relevant conduct and applicable rule as clearly as reasonably possible.

• • •

## 9.3. Temporary Suspension

**Typical circumstances:**

- Serious or repeated violations.
- Sustained harassment or intimidation.
- Repeated disruption after previous warnings.
- Conduct that creates a substantial risk to participants or project operations.

**Possible measures:**

- Temporary suspension from specified repositories or communication channels.
- Temporary revocation of contribution or moderation privileges.
- A time-limited restriction on participation in official project spaces.

The duration and scope of a suspension SHOULD be proportionate to the violation and the risk of recurrence.

• • •

## 9.4. Permanent Ban

**Typical circumstances:**

- Persistent or severe harassment.
- Credible threats or serious privacy violations.
- Deliberate sabotage or severe abuse of project privileges.
- Repeated serious violations despite previous enforcement measures.
- Conduct demonstrating that continued participation presents an unacceptable risk to the project community.

**Possible measures:**

- Permanent removal of contribution or moderation privileges.
- Revocation of access to project-controlled repositories and services.
- A permanent ban from official project spaces under the project's authority.

A permanent ban SHOULD be reserved for severe conduct or circumstances in which less restrictive measures are insufficient. Immediate permanent action MAY be justified when the severity of the incident warrants it.

# 10. Questions

## 10.1. Why Does This Project Adopt a Code of Conduct?

A code of conduct establishes clear expectations for collaboration and provides a framework for addressing harassment, abuse, and other behavior that interferes with legitimate project participation.

The project values rigorous technical debate. These rules are intended to preserve that debate by distinguishing substantive criticism from personal hostility.

• • •

## 10.2. Who Enforces These Rules?

Authorized project maintainers are responsible for enforcing this Code of Conduct within the scope of their project responsibilities.

Enforcement MUST follow the principles established in Sections 8 and 9. Where the project has a separate governance or maintainer policy, that policy SHOULD identify the individuals or roles responsible for handling reports.

• • •

## 10.3. How Do I Report an Incident?

Potential violations MAY be reported directly to an authorized maintainer through a suitable private communication channel.

Reports SHOULD include, where available:

- A description of the incident.
- The relevant date, time, and project venue.
- Links, messages, or other supporting evidence.
- Any relevant context needed to understand the conduct.

Participants SHOULD avoid publicly disclosing sensitive evidence or private information when reporting an incident.

Maintainers MUST handle reports in accordance with the confidentiality, impartiality, and enforcement requirements of this document.

Retaliation against individuals who make good-faith reports or participate in an investigation is prohibited.
